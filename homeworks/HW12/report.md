# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использовался датасет `S12-hw-dataset.csv`, прогнозировалась колонка `target` (one-step forecast, горизонт = 1).
- Данные разбиты хронологически: **train** (3024) / **validation** (648) / **test** (648).
- Сравнивались 4 подхода: B1 (naive-last), B2 (moving-average-7), B3 (Ridge на лаговых/rolling/календарных признаках), R1 (GRU).
- Лучшим подходом по val MAE оказался **R1 (GRU)** с val MAE = 5.4797. Финальная оценка на test: MAE = 6.2267, RMSE = 7.9421, MAPE = 4.03 %.
- GRU превзошла все baseline-подходы благодаря способности улавливать нелинейные зависимости в последовательности.

Нестационарность проявляется в постепенном изменении уровня ряда. MAPE порядка 4 % говорит о том, что ряд достаточно предсказуем при использовании лаговой информации.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Хронологический split: первые **70 %** — train (3024), следующие **15 %** — validation (648), последние **15 %** — test (648).
- Границы split определяются по индексам отсортированного по дате датасета; данные не перемешиваются.
- Почему `random split` здесь некорректен:
  1. **Утечка из будущего.** При случайном разбиении в train попадают наблюдения из будущего, а в test — из прошлого. Лаговые и rolling-признаки для тренировочных точек будут содержать значения из test, что делает оценку нечестной.
  2. **Нарушение каузальности.** В реальности модель всегда прогнозирует будущее на основе прошлого; temporal split воспроизводит эту ситуацию.
  3. **Автокорреляция.** Соседние наблюдения сильно зависимы; при random split близкие по времени точки попадают в разные части, искусственно завышая метрики.
  4. **Завышенная оценка качества.** Метрики на random split не отражают реальную способность модели прогнозировать вперёд.

### 4.2. Признаки для baseline-моделей

- Лаги: `lag_1`, `lag_7`, `lag_14`
- Rolling-признаки: `rolling_mean_7`, `rolling_std_7` (со сдвигом `shift(1)`, чтобы не включать текущее значение)
- Календарные признаки: `day_of_week`, `month`, `day_of_month`, `day_of_year`
- Пропуски после построения лагов/rolling: первые ~14 строк удалены (`dropna`), так как для них невозможно корректно вычислить lag_14 и rolling-окно
- Масштабирование: `StandardScaler`, обучен **только на train**; `transform` применяется к val и test

## 5. Модели и эксперименты (B1, B2, B3, R1)

- **B1 (naive-last):** прогноз = предыдущее известное значение (`lag_1`). Не требует обучения. Простейший baseline, показывающий нижнюю границу адекватности.
- **B2 (moving-average):** прогноз = скользящее среднее 7 предыдущих значений (`rolling_mean_7`, сдвинутое на 1). Сглаживает шум, но запаздывает при резких изменениях.
- **B3 (ridge-lag-features):** `Ridge(alpha=1.0)` на 9 признаках (3 лага + 2 rolling + 4 календарных). Линейная модель, учитывающая множество лагов и сезонную структуру одновременно.
- **R1 (gru-forecast):** `GRU(hidden_size=64, num_layers=1)` на оконном представлении ряда длины 14. Нелинейная рекуррентная модель, способная обучаться сложным паттернам.

Дополнительно:

- Основная метрика выбора лучшей модели: **val MAE**
- Дополнительные метрики: RMSE, MAPE
- `window_size` для GRU: **14**
- Batch size: **32**
- Максимальное число эпох: **100**
- Optimizer: **Adam**
- Learning rate: **0.001**
- Как сохранялась лучшая модель: по минимуму val MAE на каждой эпохе сохранялся `state_dict()` в `artifacts/best_gru.pt`

## 7. Анализ

Наивный baseline B1 (naive-last) оказался surprisingly сильным: val MAE = 6.44 — это лишь на 1.7 % хуже, чем Ridge B3 (6.34). Это объясняется тем, что при дневном горизонте предыдущее значение уже содержит значительную часть информации о текущем, особенно если ряд не имеет резких скачков.

Moving-average B2 показал значительно худший результат (val MAE = 12.70, почти вдвое хуже B1). Скользящее среднее по 7 значениям чрезмерно сглаживает ряд и систематически запаздывает, что приводит к большой ошибке на участках с изменением уровня или локальными колебаниями.

Ridge B3 на лаговых, rolling- и календарных признаках лишь немного превзошёл naive baseline (MAE: 6.34 vs 6.44). Это говорит о том, что линейная комбинация лагов и сезонных фичей добавляет лишь небольшой прирост для данного ряда — основная предсказательная сила сосредоточена в lag_1.

GRU (R1) показала лучший результат по всем метрикам на validation (MAE = 5.48, RMSE = 7.05, MAPE = 3.69 %). Рекуррентная архитектура позволяет улавливать нелинейные зависимости в окне длины 14, которые недоступны линейной модели. Лучшая эпоха — 42 из 100, что свидетельствует о разумной ранней остановке и отсутствии переобучения.

На test GRU показала MAE = 6.23 (рост на ~13 % по сравнению с val), что ожидаемо: test-период может иметь несколько иную статистику. Тем не менее R1 осталась лучшим подходом и на test.

Тренд и сезонность ряда заметны визуально и отражаются на прогнозе: модели, не учитывающие недельную структуру (B2), существенно проигрывают. Календарный признак `day_of_week` в B3 и неявное обучение сезонных паттернов в GRU помогают.

Возможные утечки данных в такой задаче: (а) random split — лаговые признаки содержат будущие значения; (б) fit scaler на всех данных; (в) rolling-статистики без shift; (г) использование test для подбора гиперпараметров. Все эти источники в данной работе исключены.

Выбор лучшей модели по validation, а не по test, принципиален: test имитирует реальное «будущее», и если подбирать гиперпараметры по нему, оценка будет оптимистичной и не перенесётся на новые данные.

## 8. Итоговый вывод

Для one-step forecast на данном ряде **GRU** на оконном представлении показала лучший результат (val MAE = 5.48, test MAE = 6.23), превзойдя как наивные baseline, так и Ridge на инженерных признаках. Тем не менее Ridge на лаговых и календарных признаках является сильным и вычислительно дешёвым baseline, подходящим для быстрого прототипирования — его результат лишь на ~16 % хуже GRU по val MAE.

Простые методы (naive, MA) достаточны как нижняя граница качества и для sanity-check: если сложная модель не превосходит naive, это сигнал о проблемах с постановкой задачи или данными.

Переход к GRU и другим нейросетям оправдан, когда данных достаточно (здесь ~3000 train-точек — уже на границе), зависимости нелинейны, а прирост качества критичен для бизнес-задачи.

Главный вывод о валидации: **корректный хронологический split и отсутствие утечек из будущего — необходимое условие доверия к метрикам** модели временных рядов. Без этого любые числа на test бессмысленны.
